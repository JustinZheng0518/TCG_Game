# 小小卡店：玩法、渠道和行情来源

电脑与手机共用同一套经营流程：进货 → 选择拆封或保留库存 → 收藏 / 买卖 / 寄售单卡 → 营业结算 → 新一天的行情与任务。全部为本地、单人、虚拟货币模拟，没有真实支付。

## 商品与获取渠道

不能因为一个 set 只有几张卡就判定它是活动卡，也不能把所有 set 都按五张 RR 包抽取。本次依据源数据的商品类型、名称及已查阅的官方说明，把 236 套划为八类：

| 渠道 | 数量 | 游戏获得方式 |
| --- | ---: | --- |
| 常规补充包 | 42 | 供货商进货，库存可拆封或留店出售；每包 5 张，沿用 RR 独立保底、最高档每包 0.1% 的游戏规则 |
| 特色零售包 | 12 | 单独的零售商品；宝石包采用 4 张体验，其余专题包采用单张体验，不使用普通包 RR 规则 |
| 预组与构筑 | 24 | 可进货、整盒出售；拆封为 60 张模拟配方，不宣称还原实体卡组清单 |
| 礼盒与套装 | 85 | 选择特典卡面对应款式订购，每天限一份，并附 1 张游戏活动券 |
| 赛事与活动 | 32 | 模拟完成活动，取得一张参加奖、2 张券和 3 点口碑；每天限一次 |
| 任务奖赏 | 10 | 完成经营任务赚活动券，用 2 张券领取本套随机一张 |
| 特典兑换目录 | 3 | 汇总多种来源的特典，用 3 张游戏活动券选择一张；不声称这些特典全部由官方兑换码发放 |
| 组合附属包 | 28 | 与普通零售包分离；用 1 张券领取随机单张体验卡，体现附属奖励渠道 |

分类数据位于 `data/shop/products.json`，可通过 `python tools/build_shop_catalog.py` 重建。没有逐卡核实的来源保留“按商品名称与源类型归类”的说明，不将分类推断当作官方逐卡发放记录。`151C` 的“活动包”按名称单独划入活动渠道。

**游戏改编范围：** 大多数特色包、附属包、礼盒及预组不复刻实体商品的完整封入、配件、套装关系或主题卡组配方。礼盒体验只领取所选特典；预组配方为 58 张基础 + 2 张主力的模拟组合。卡表仍可查看全部收录卡，完整卡表中也提供单卡买入。因此特殊渠道不会悄悄套用五张普通包，也不会让某些卡面永久不可获得。

### 兑换码

`START-STORE` 为游戏新店礼包，给予 ¥100 和 3 张活动券，一次性领取。每天的店长通讯提供 `SHOP-DAY-0001` 这种当日游戏码，给予 1 张券且只能兑换一次。现实中的官方兑换码不在本游戏核销。未找到足以逐卡核实哪些综合特典由代码发放的资料，因此不伪造官方代码、也不把所有活动特典称为兑换码卡。

## 资金与交易

初始资金 ¥3,000，单位为整数“分”，避免小数累计误差。旧版收藏自动迁移，保留全部卡牌并建立新店资金；后续动作都把卡牌、现金、库存、寄售和账本放入同一个存档，写入失败则全部不生效。

- 供货价为当日模拟行情的 72%；营业时未拆封商品顾客价为行情的 95%。每日期初供货额度为 40 件，升级增加额度。
- 进货扣现金、增加未拆封库存；拆封扣库存、增加卡牌，不重复扣钱。
- 单卡行情价可来自外部报价或模拟估值；买入价为 120%、即时回收为 70%、寄售到账为 92%，形成买卖价差。
- 寄售时卡牌移出可出售收藏，放入寄售柜；未成交保留，下架返回收藏。不会同时出售同一份卡。
- 批量卖重复卡只处理当前套装，每款至少保留 1 张。单张卖出 / 寄售允许处理最后一张，是玩家主动操作。
- 营业结算按口碑、等级和库存分配有限顾客，卖出货架商品及部分寄售卡，收取基础 ¥15 日常运营费用；升级后费用增加。结算前自动发放已达标但未领取的经营任务奖励。
- 每天打理店铺可获得 ¥50 服务收入和 1 点口碑；即使现金不足仍有继续经营的途径。
- 升级花费为当前等级 × ¥500，最高 10 级，增加供货与接客能力。

## 行情与新闻的联网方式

### 官方售价与新闻快照

`data/shop/market-feed.json` 保存有来源链接、抓取时间的官方售价参考及新闻。目前有 **4 款商品的官方售价锚点、16 条官方资讯**，不是“全库实时成交价”。其他商品明确使用模拟定价。

`python tools/refresh_market.py` 从官方首页更新资讯，并核对已支持商品的准确售价措辞；每个来源请求设 25 秒整体超时，工作流设 4 分钟上限。解析失败保留原值和原抓取时间，不把其他商品售价错配过来。`.github/workflows/market-refresh.yml` 配置每天 UTC 03:17 和手动触发更新。GitHub 定时任务可能延迟，外部站点不可用时保留上次快照。

游戏先读取随站点发布的快照，再联网向本仓库 main 分支请求最新快照；工作台也可手动刷新。因此数据更新不依赖一次新的 Pages 页面构建。刷新失败会显示原因并保留已有行情。

### 单卡联网查价

公开的 [Cardfolio 项目](https://github.com/legohaha98/ptcg-cardfolio) 记载 Kyo Cards 简中查询使用 `productLine=PKCN` / `productType=SING`，人民币字段为 `data.metadata.card.jihuansheMarketPrice`。本游戏据此实现浏览器直连查询：

1. 在卡牌详情点“联网查询简中单卡报价”。
2. 搜索返回同名候选，展示套装、卡号和稀有度。
3. 用户核对版本，查询该候选的人民币市场参考价。
4. 再点“已核对版本，将报价用于此卡”，才将报价映射到本库精确卡面 ID；不会因同名自动覆盖。

报价来源和抓取时间写入经营存档并可备份。无报价、零值、负值、异常单位或网络 / 跨域失败时，不覆盖已有价格。外部的市场价字段不是实际成交证明。本次云网络访问 `kyocards.com` 被代理以 403 阻断，**没有实测确认服务当前可用**；接口处理与版本确认流程已用受控响应验证，真实使用仍依赖该服务及浏览器网络 / 跨域支持。未取得真实报价的卡继续显示“模拟估值”。

### 可选自选行情 JSON

工作台支持 HTTPS JSON URL，需要浏览器跨域可读。必须标明 CNY、zh-CN，并使用本库的 `SET:source_card_id` 精确卡面 ID；不能把英文、日本版或同名卡直接映射过来。每个报价必须包含正整数分、来源链接和抓取时间。

```json
{
  "schema_version": 1,
  "currency": "CNY",
  "language": "zh-CN",
  "updated_at": "2026-10-17T12:00:00Z",
  "products": {},
  "news": [],
  "cards": {
    "SET:123": {
      "cents": 1234,
      "source_url": "https://你的数据来源/对应卡面",
      "observed_at": "2026-10-17T12:00:00Z"
    }
  }
}
```

示例 ID 为占位符，实际导入会核验套装及卡面存在。不能缺少来源、使用不存在的卡、或直接按名称匹配。接入会保存报价，只有通过校验和存档写入成功才会生效；全部失败时保留现有数据。

### 新闻如何影响价格

工作台同时展示“模拟经营新闻”和带官方原文 / 日期的真实新闻。补货、赛事热潮、收藏热度等模拟事件按营业日切换，影响包价与卡价；官方新闻也会触发明确标记的**游戏推演**，例如新品消息对应包价 -2%、单卡 +2%。这只是玩法因果，不代表该新闻在真实市场造成了这些涨跌。

行情另有确定性的每日 / 商品波动，同一天刷新或反复点开不会重新掷价格。外部参考价仍会参与游戏波动与买卖价差；页面分开展示参考来源和经营估值。

## 存档与验证

存档版本 2 保留原 `counts`，新增 `shop`（现金、日数、库存、寄售、任务、已用码、外部报价和最近账本）。沿用原浏览器存储键，首次成功操作时原子保存新结构。

- 恢复版本 2 备份会先显示现金与日数，确认后替换整份经营存档，不累加资金。
- 导入旧版收藏只合并收藏，不重置现有资金；重复导入相同旧备份不会重新补回已出售的卡。
- 本地单机存档可由玩家编辑，不提供服务器账户、跨设备自动同步或防作弊承诺。

运行：`node --test tests/*.test.cjs`，以及 `python3 -m unittest discover -s tests -p 'test_*.py'`。测试覆盖原开包概率、渠道约束、资金与库存守恒、任务及码的单次性、寄售、存档迁移、89/10/1 活动配比、数据验证及失败不变更。浏览器验收覆盖电脑和手机的完整经营流程、导入导出、外部接口失败回退及存储失败。
